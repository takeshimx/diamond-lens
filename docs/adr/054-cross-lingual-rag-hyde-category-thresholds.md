# ADR-054: 公式ルール PDF を検索対象に復帰させ、カテゴリ別閾値と HyDE でクロスリンガル検索を成立させる

- Status: Accepted（`USE_GLOSSARY_HYDE` を追加、`EXCLUDED_CATEGORIES` を空に）
- Date: 2026-09-04
- Deciders: プロジェクトオーナー
- 関連: [[047-rag-chunking-multilingual-embeddings-reranking]]（本 ADR はその続き）

## Context（背景・課題）

[[047-rag-chunking-multilingual-embeddings-reranking]] で用語集 RAG を BigQuery 上に再構築した後、Tier 2（MLB 公式ルール PDF、897 チャンク）を取り込んだ。しかし rule 型の命中@3 が **0.333** に留まったため、2026-08-21 に `EXCLUDED_CATEGORIES = ("rules",)` で検索対象から除外し、**データを残したまま無効化**した状態が続いていた。

再開にあたり実データを調べたところ、**この 0.333 という数字自体が測定誤りを含んでいた**。

### 発見 1: ゴールデンセットの正解が「中身のない見出し」を指していた

`rule_001`（「ボークが宣告されるのはどんな場合ですか」）の正解に指定していた `#6.02(a)` の全文は 134 字で、次の内容しか無かった。

```
(a) Balks
If there is a runner, or runners, it is a balk when:
```

ボークの条件は `6.02(a)(1)`〜`(13)` の 15 チャンクに分かれている。検索がそれらを返しても不正解と記録され、この空のリード文が **414 位**だったことをもって「検索が壊滅的」と判断していた。**正解ラベル側の誤りである。**

### 発見 2: n=3 では何も判断できない

rule 型はわずか 3 問だった。0.333 は「3 問中 1 問」であり、1 問の当たり外れで 0.333 単位に跳ねる。判断材料になっていなかった。

### 発見 3: 用語集とルールは言語構成が異なる

ADR-047 は「クロスリンガル検索が 1 モデルで成立」と記録したが、それは Tier 1 での観測である。実際には次の差がある。

| | 質問 | 文書 |
|---|---|---|
| Tier 1 用語集（43 件） | 日本語 | **日本語**（`docs/knowledge/*.md` は自前で日本語執筆） |
| Tier 2 ルール PDF（897 件） | 日本語 | **英語** |

**日英を跨いでいるのは rules だけ**であり、その条件下で閾値の妥当性は一度も検証されていなかった。

## Decision（決定）

### 1. ゴールデンセットを作り直す（測定の是正）

- 正解 chunk_id を実体チャンクへ貼り直す。`_rules` に「リード文チャンクを正解に指定しない」を明文化
- rule 型を **3 問 → 30 問**へ拡張。型の配分は「実際の聞かれ方」に寄せる

| subtype | 問数 | 内容 |
|---|---:|---|
| situation | 9 | 場面を描写して条文を引く |
| paraphrase | 8 | 専門語を一切使わない |
| enumeration | 6 | 「どんな場合か」。正解が十数チャンクに分散 |
| definition / spec / confusable | 6 | 既に満点。回帰検知用に維持 |
| citation | 1 | 条文番号の直接指定。**改善目標からは除外**（実利用者が聞かない型） |

- 「既存の問題は変更しない」という自ルールに、**正解ラベル自体が誤っていた場合のみ修正可**という例外を追加した。誤った基準で測り続ける害の方が大きい

### 2. 距離閾値をカテゴリ別にする

`CATEGORY_DISTANCE_THRESHOLDS = {"rules": 0.35}`。用語集は 0.275 のまま。

日英を跨ぐと距離分布が約 0.07 遠い側へ寄るため、用語集用に決めた 0.275 では候補が全て足切りされ、**リランクが起動しないまま終わっていた**（30 問中 15 問で候補 0〜1 件）。

### 3. HyDE（クエリ書き換え）を導入する

`query_rewrite_service.py`。日本語の質問を **英語の条文風テキスト**へ LLM に書き換えさせ、それを埋め込んで検索する。ユーザーの入力も最終回答も日本語のままで、書き換わるのは検索に使う文字列だけ。

適用対象は `HYDE_CATEGORIES = ("rules",)` に限定する。用語集は日本語文書のため、英訳すると逆に遠ざかる。

### 4. `category` をツール引数の必須項目にする

`"required": ["query", "category"]`。閾値と HyDE の適用判定が `category` を鍵にしているため、省略されると設定が既定値に落ち、改善が全て無効になる。

### 5. 補助 LLM 呼び出しに `node` を持たせる

`call_gemini(node=...)` を追加し、リランク（`node="reranker"`）と HyDE（`node="hyde"`）に付与する。

## Alternatives Considered（検討した代替案）

- **ツールを `rules_search_tool` として分離する**: `category` をコード側で固定でき、LLM の選択ミスを構造的に排除できる。ただし `required` の追加（1 行）で「省略」のケースは消え、残るのは「誤選択」のみ。まず安い手から試すべきと判断し**保留**。誤発火の実測で問題が出た場合に再検討する。
- **テーブル・サービスを `knowledge_base_*` に改名する**: 名前は実態と乖離しているが、検索機構は完全に同一であり、分離すると SQL・サービス・評価ハーネスが二重化する。影響範囲の割に機能が変わらないため**却下**。LLM から見える顔（ツールの description）だけを実態に合わせた。
- **ユーザーに英語で質問させる**: 論外。実装の都合をユーザーに押し付けることになる。HyDE は同じ効果を内部処理だけで得る。
- **HyDE を全カテゴリに適用する**: 用語集は日本語文書のため英訳は逆効果。カテゴリで線を引く。
- **書き換え結果と元の質問の両方で検索して RRF で統合する**: `rule_016` のような「元の質問の方が良い」ケースを救えるが、埋め込み API が 1 回増える。効果が未検証のため**今回は見送り**。
- **閾値を全体的に緩める**: 用語集は 0.275 で命中@3 1.000 に達しており、緩めてもノイズが増えるだけ。カテゴリ別にするのが正しい。

## Consequences（結果・トレードオフ）

### 実測結果（rule 型 30 問、リランク ON）

| 構成 | 命中@3 | 命中@5 | MRR |
|---|---:|---:|---:|
| 閾値 0.275（用語集と同じ） | 0.600 | 0.667 | 0.580 |
| + rules 専用閾値 0.35 | 0.733 | 0.733 | 0.708 |
| **+ HyDE** | **0.833** | **0.867** | **0.766** |

全 40 問では 命中@3 **0.850** / MRR **0.793**。誤発火率は `rules` を解禁した状態で再測定し **0.000（0/7）**。

### 日英ギャップの定量化

`rule_020`（「ストライクゾーンを外れた投球を4つ受けた打者はどうなりますか」／正解 `def:BASE ON BALLS`）で切り分けた。

| 検索に使った文字列 | 正解の順位 | 距離 |
|---|---:|---:|
| 日本語の質問そのまま | **212 位** | 0.3244 |
| 同義の英文 | **16 位** | 0.2450 |

正解チャンクには `receives four pitches outside the strike zone` と、質問とほぼ逐語対応する英文が入っている。**語彙が一致していても、日本語のままでは 212 位**だった。

同時に、英語でも 16 位止まりであることから、**日英ギャップだけが原因ではない**ことも分かった。897 チャンクが同一の法律英語・同一のテンプレートを共有しており、距離帯が狭い（1 位 0.2190 と正解 0.2450 の差が 0.026）。ADR-047 が用語集 43 件で記録した識別力低下と同型の現象が、規模 20 倍で起きている。

### この設計で分かった、記録すべき失敗

**「精度が出ない」と判断して機能を無効化したが、実際は測定が壊れていた。** 保留の根拠だった 0.333 は、空のリード文を正解に指定していたことによる。ラベルを貼り直すと同じ質問の順位は 414 位 → 25 位になった（それでも上位 5 件には届かないが、桁が違う）。

**さらに、その誤った測定が次の判断も歪めていた。** 「リランクを入れても rules は改善しなかった」という観測は、閾値 0.275 で候補が全滅し**リランクが一度も起動していなかった**ことによる。原因を測らずに「リランクは効かない」と結論づけていた。

教訓は、**精度の数字を疑う前に、その数字を作っている測定系を疑う**こと。

### HyDE の限界

net では明確にプラスだが、万能ではない。

| 型 | 効果 |
|---|---|
| 状況を説明して条文を探す | **改善**（`rule_022` 死球 126 位 → 上位 5 件内） |
| 用語名を答えさせる | **悪化**。`rule_016`（ランダウン）は書き換え文に `run-down` が入らず 180 位へ |
| 条文番号で引く | **悪化**。書き換えで番号が消える（対象外の型のため実害なし） |

### レイテンシ

ルール質問 1 件あたり **20〜35 秒**（HyDE 約 10 秒 + リランク約 19.5 秒 + その他）。ADR-047 は「リランク 2〜15 秒」と記録していたが、それを上回る。HyDE の結果で検索し、その結果をリランクする直列構成のため**並列化できない**。短縮するならリランクの候補数削減が候補。

### 悪くなったこと / 新たな負荷

- **ルール質問 1 件につき Gemini が 2 回**（HyDE + リランク）。用語集の質問は 1 回（リランクのみ）
- 上記のレイテンシ
- **`node` 未指定の副作用が顕在化した**。`call_gemini` は `node` を設定しないため、リランクのログ行（中身は候補番号の配列）が `trace_query_service` で「エンドポイントのサマリ行」と同一視され、Trace Viewer の FINAL RESULT に配列が表示されていた。`node` の付与と、サマリ行を `total_latency_ms` の有無で選ぶ防御の両方を入れた（[[053-agent-trace-viewer-failure-labeling]]）
- **Tier 2 のチャンク品質は未修正**。ページ柱の残留 12.8%、リード文だけのスタブ 4.6%、`def:WIND-UP POSITION` が 28 分割される等の取り込みバグが残っている。再取り込み（埋め込み 897 回）が必要なため別作業とした

## JD Alignment（この募集要件との対応）

- **評価**: 「精度が出ない」で止めず、測定系の欠陥を実データで特定して是正した経緯を、数字の変遷（0.333 → 0.833）とともに説明できる。n=3 の指標を信用しない判断も含む
- **多言語 RAG**: クロスリンガル検索の劣化を「212 位 vs 16 位」という単一実験で定量化し、対策（HyDE）と残存要因（識別力不足）を分離した
- **失敗の分析**: 無効化の判断そのものが誤った測定に基づいていたことを認め、記録している
